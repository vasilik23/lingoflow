## Безопасность и воспроизведение

Для повторения использовать отдельного обычного ученика, новый run_id
и локальную копию текущего кода. Подменять только HTTP-вызов репозитория
`b1_run_store`, проверяя точные user_id/run_id до записи. После каждого шага
читать строку настоящим bearer этого ученика, а после завершения независимо
проверить SQL и убрать только созданную fixture. Не отключать production
хранилище, не менять глобальные таймеры, RLS или grants.

Локальный macOS SDK первоначально не доверял цепочке сертификатов стандартного
`urlopen`. Для приёмки задан `SSL_CERT_FILE` на установленный certifi CA bundle;
TLS-проверка сохранена. Предварительные неуспешные запуски строк не создали.

Проверены действующие owner-only SELECT/INSERT policies. Схема, grants и RLS
не менялись. Security advisors без новых замечаний: прежние 11 INFO о закрытых
таблицах без policies, WARN о намеренном защищённом RPC лимитов и WARN
об отключённой проверке скомпрометированных паролей. Справка:
[закрытые таблицы](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy),
[RPC](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable),
[пароли](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
Контракт повторной вставки сверен с
[документацией Supabase](https://supabase.com/docs/reference/dart/upsert).
