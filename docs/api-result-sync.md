# Проектирование отправки результатов и offline-синхронизации

Документ фиксирует следующий контракт для отдельного мобильного/PWA-клиента.
Online endpoint и серверное событие реализованы; управляемая клиентская
offline-очередь подключена к 15 урокам трёх пилотных тем A1/A2/B1 и не является
обещанием полного offline-режима. Разрешённые ID перечислены явно; новые темы
не подключаются автоматически.

## Граница контракта

`POST /api/v1/me/lesson-results/` принимает Supabase bearer token и
результат только текущего пользователя. `user_id` не передаётся в теле: Django
получает его из проверенной сессии, а запись в Supabase выполняется с тем же
access token через owner-scoped RLS.

Минимальный запрос содержит:

- `event_id` — UUID, созданный клиентом один раз до первой попытки отправки;
- `lesson_id`, `plan_date`, `completed_at`;
- `cards_total`, `cards_known`;
- `contract_version` и необязательный `client_instance_id` для диагностики.

Сервер проверяет существование активного урока, диапазоны чисел, допустимую
дату и размер запроса. Токены, email и профиль в payload запрещены.

## Идемпотентность

Уникальная граница — `(user_id, event_id)`. Сервер хранит hash нормализованного
payload вместе с immutable событием.

- первая валидная попытка создаёт событие и возвращает `201`;
- повтор того же `event_id` с тем же hash возвращает прежний результат и `200`;
- тот же `event_id` с другим payload возвращает `409 idempotency_conflict`;
- сетевой timeout после записи безопасно повторяется с тем же `event_id`.

Текущая `lesson_completions` становится серверной проекцией событий. Повторная
синхронизация не уменьшает уже подтверждённый прогресс и не создаёт второй
completion за тот же урок и дату.

## Offline-очередь и конфликты

Клиент может хранить только минимальный payload и статус события в IndexedDB
или защищённом хранилище приложения. Access/refresh token не входит в очередь.
Отправка начинается после восстановления сети и действующей сессии; при `401`
очередь остаётся локально и интерфейс просит войти снова.

События отправляются по времени создания, но сервер не доверяет порядку
доставки. Успешные элементы удаляются только после ответа с подтверждённым
`event_id`. Ошибки `409` и постоянные `4xx` требуют видимого решения
пользователя; временные `5xx` повторяются с ограниченным exponential backoff.
Очередь показывает количество ожидающих результатов и позволяет отказаться от
неотправленных данных.

## Реализовано и следующий этап

1. ✅ Совместимая immutable event-таблица описана парными Django/Supabase
   миграциями; существующая completion-запись обновляется в той же транзакции.
2. ✅ RLS и grants ограничены `authenticated SELECT/INSERT`, владелец берётся
   только из `(select auth.uid())`, RPC работает как `security invoker`.
3. ✅ Duplicate/retry/conflict, BOLA, bearer-only и размер payload закреплены
   regression-тестами.
4. ✅ Security/performance advisors и production smoke выполнены перед
   контролируемым включением клиентской offline-очереди.
5. ✅ Изолированный браузерный прототип очереди находится в
   `learning/static/polskiflow/result-queue.js`: он разделяет данные по
   пользователям, дедуплицирует их по `event_id`, не сохраняет токены и
   различает ожидание авторизации, временную ошибку и конфликт.
6. ✅ Для браузера добавлен same-origin handoff
   `POST /api/v1/me/lesson-results/session/`: он принимает cookie-сессию только
   с валидным CSRF-токеном, отвергает `Authorization` и передаёт access token в
   owner-scoped Supabase RPC исключительно на сервере. `flushSession` использует
   этот endpoint, поэтому bearer не попадает в JavaScript или IndexedDB.
7. ✅ Скрипт загружается на страницах уроков, а allowlist разрешает постановку
   в очередь результатов 15 уроков тем «Знакомство», «Жильё и услуги» и
   «Биография и опыт» только после временной сетевой/5xx ошибки.
   Автоматизированный recovery-тест подтверждает безопасный повтор и удаление
   совпавшего события. Браузерный recovery-smoke на Vercel Preview выполнен
   14 сентября 2026: очередь сохранила неизменный payload,
   отправила тот же event через session endpoint, очистилась после HTTP 201,
   а «Сегодня» обновился с 0/4 до 1/4. После поэтапного rollout этот же
   безопасный event-поток был включён для четырёх ID первой темы A1.
8. ✅ 15 октября расширение на все три пилота проверено в изолированной копии
   Django с настоящим QA-аккаунтом и production Supabase. Четыре результата
   прошли отказ → IndexedDB → session handoff → реальное событие/проекцию;
   повтор тех же событий не создал дубликатов. Сообщение на карточке относится
   только к её event_id и не обещает назначение повтора по одному receipt.
   [Протокол и следующая календарная проверка](pilot-result-recovery-2026-10-15.md).
