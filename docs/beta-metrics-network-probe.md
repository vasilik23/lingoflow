# Сетевой замер Supabase · подготовка и недостающий ключ

**Инструмент подготовлен; настоящий сетевой замер ещё не выполнен.**
Проверка имён настроек 25 октября: локально и в Vercel есть URL и публичный
anon-ключ, но нет серверного ключа для service-only RPC. Подключение Supabase
MCP работает для управления БД, однако не предоставляет этот REST credential.
Результаты management API или HTTP 401 не выдаются за стоимость сборщика.

## Одно действие владельца

1. Открыть Supabase → проект LingoFlow → **Settings → API Keys**.
2. Создать отдельный **Secret key** для диагностического замера.
3. В локальном `backend/.env.metrics-probe.local` заполнить
   `BETA_METRICS_SERVICE_KEY=` и сообщить «готово». Сам ключ в чат не отправлять.

Файл уже создан с правами 0600, исключён из Git. Он читается только операторской
командой, не загружается обычными Django settings. Заполнение файла не включает
сбор в приложении и не устанавливает ключ в Vercel. После эксперимента отдельный
ключ можно отозвать, а локальную копию удалить.

Новые `sb_secret_…` — не JWT: исправлена передача только в `apikey`;
legacy service-role JWT сохраняет Bearer-совместимость. Это соответствует
[официальному контракту ключей](https://supabase.com/docs/guides/getting-started/api-keys#known-limitations).
Полный живой вызов с новым ключом до его предоставления не заявляется проверенным.

## Готовые этапы проверки

`manage.py beta_metrics_network_probe --release FULL_PRODUCTION_SHA --runs 5`
выполняет 2–10 последовательных HTTPS-вызовов только фиксированного
`habcghygjaynknkcbirz.supabase.co/rest/v1/rpc/beta_collect_request`.
По умолчанию используется UUID несуществующего участника. Оператор до запуска
проверяет отсутствие sentinel в auth/membership и фактический deployment/SHA.
Ожидается HTTP 200 + JSON null, без записи диагностики, попыток или результатов.
Это проверка сети/авторизации и раннего возврата, **не цена enrolled collector**.

Далее оператор через уже подключённый Supabase временно зачисляет существующий
разрешённый QA-аккаунт в отдельную `operator-network-*` когорту на срок не более
15 минут, предварительно убедившись, что прежней membership нет. Не заменять
существующую строку и не использовать реальных участников.
Команда с `--context qa` читает только QA_USER_ID из существующего приватного
`backend/.env.qa-20261014.local`; произвольного user ID в CLI нет.
Этот режим создаёт синтетические request observations: `today/GET/200`, app_ms=0.
Он не резервирует попытку, не выполняет урок и не пишет учебные результаты.
Ожидается объект с null attempt_id/finished_at. Оператор отдельно проверяет
точный cohort/count, затем удаляет только созданные диагностические строки
и membership. Не включать эти наблюдения в человеческую beta.

Глобальный флаг остаётся false. Сам инструмент не зачисляет участников и
не меняет их настройки. Ошибки/таймауты считаются отдельно, при неожиданном
ответе серия прекращается. Redirect не выполняется, ключ не передаётся другому
хосту. В выводе нет ключа, user ID, email, сырых headers/body или provider errors.
Читаются только приватные файлы владельца без symlink и прав доступа группы.

## Как трактовать результат

Время — весь HTTPS RPC с операторского компьютера, включая сетевые операции.
Это не Vercel → Supabase, не Django/рендер/INP и не live cost веток
reserve/finish. Эти поля остаются null; `beta_readiness_evidence=false`.
Даже успешная nonmember проверка не закрывает стоимость записи enrolled запросов.
Поле `enrollment_performed=false` означает только то, что сама команда
не меняет membership; в QA-режиме оператор готовит её отдельно.

После получения ключа: выполнить nonmember preflight → QA observation probe с
операторской проверкой/очисткой → измерить реальный Vercel-путь на отдельном
QA Preview, не включая сбор в production. Перед активацией для людей остаётся
согласование состава данных/срока/условий участия и бюджета задержки.
Никакого нового требования к уже принятому ручному retention-процессу нет.
