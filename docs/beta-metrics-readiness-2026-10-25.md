## Очистка в production

Установлен Supabase `pg_cron`. Единственная новая задача
`lingoflow-beta-metrics-purge` активна ежедневно в **02:15 UTC** (`15 2 * * *`,
cron timezone GMT). Она выполняет `private.beta_purge()` и удаляет только свою
историю запусков старше семи дней. Нет HTTP, новых ключей, почты, удаления
аккаунтов, учебных результатов или истории других задач.

Для проверки настоящего scheduler job временно переведён на интервал 1 секунда;
в `cron.job_run_details` подтверждены `succeeded`, в том числе
25 октября 08:47:48 UTC. После проверки восстановлено ежедневное расписание;
временных jobs не осталось. Диагностические таблицы production после проверки:
**0 участников / 0 попыток / 0 запросов**. Тестовые данные в production не вставлялись.

Порог удаления диагностических запросов/попыток уменьшен до **29 дней**:
при ежедневном исполнении это даёт запас до целевых 30 дней. Просроченная
membership удаляется с диагностическими попытками каскадом. Учебные данные
не затрагиваются. Локальные SQL-тесты подтверждают удаление записи возрастом
29 дней 1 час и сохранение записи 28 дней 23 часа и учебного результата.

Это не гарантия при простое базы/планировщика. Перед включением и при
операторском контроле выполнить [агрегированный status query](../ops/beta-metrics-status.sql):
нужны активное правильное расписание, последний запуск `succeeded` не старше
26 часов и отсутствие диагностических записей старше 30 дней. Автоматический
alert на сбой этого job данным срезом не настроен.

Миграции применены по порядку; версии файлов совпадают с production ledger:
`20261025084642_beta_purge_retention_margin.sql`,
`20261025084650_schedule_beta_purge.sql`. Отдельный PostgreSQL CI проверяет
purge; настоящий `pg_cron` проверен в Supabase, а не имитируется в обычном
PostgreSQL 17 CI image без этого расширения.

## Изолированный стенд и сверка

[Воспроизводимый lab script](../ops/beta-metrics-lab.py): Django test Client →
настоящий loopback HTTP RPC bridge → отдельный PostgreSQL 17.
Только сгенерированный fixture-пользователь и `operator-lab`; без настоящего
Supabase ключа/участника. Копия локального SQLite содержит учебный контент;
сохранение результатов и диагностический SQL выполняются в локальном PostgreSQL.
RPC исполняется под service_role, проверяя реальные grants/RLS.

В каждой серии по 10 пар on/off, порядок чередуется. Перед измерением —
два прогревочных прохода обоих режимов, их диагностические записи исключены.
Две серии: без добавленной задержки и с **искусственными 50 ms на RPC**.
Это не фактический RTT Supabase и не production/browser/field INP benchmark.
Финальный шаг получает подписанное состояние последней карточки из harness:
проверяется серверный путь завершения, не прохождение всего урока человеком.

Итог: **80 ожидаемых запросов = 80 полученных; 20 начатых = 20 завершённых =
20 подтверждённых сохранений; pending_confirmation = 0**. 132 RPC с учётом
прогрева. Выключенные проходы в счётчики не попали. Сценарии offline A → B →
поздняя запись A, refresh, повторная доставка и owner isolation дополнительно
покрыты `supabase/tests/beta_metrics.sql`. Данные стенда удалены после проверки.

## Замер

Миллисекунды, nearest-rank p50/p95, n=10 на режим в каждой строке.
При таком n p95 равен максимуму; это небольшой диагностический срез.

| Действие | Добавлено на RPC | Off p50 / p95 | On p50 / p95 |
| --- | --- | --- | --- |
| Сегодня | 0 | 11.5 / 12.4 | 22.7 / 25.9 |
| Открытие урока | 0 | 9.9 / 11.0 | 37.9 / 39.7 |
| Раскрытие карточки | 0 | 12.7 / 14.2 | 27.6 / 30.9 |
| Завершение | 0 | 19.5 / 23.4 | 48.3 / 51.7 |
| Сегодня | 50 ms | 12.6 / 25.5 | 88.8 / 122.0 |
| Открытие урока | 50 ms | 12.0 / 33.0 | 163.7 / 214.0 |
| Раскрытие карточки | 50 ms | 14.0 / 27.7 | 91.5 / 110.5 |
| Завершение | 50 ms | 22.1 / 51.5 | 177.0 / 260.5 |

Вывод: синхронная доставка добавляет примерно 11–29 ms p50 даже на loopback;
в сценарии с добавленными 50 ms — примерно 76–155 ms. Особенно дороги открытие
и завершение, где выполняется два RPC. Это основание **не включать текущий
сбор массово**. Синхронные обращения уже сокращены в следующем срезе;
приведённые здесь замеры относятся к прежнему варианту. Дальнейшее вынесение доставки
за пределы пользовательского ответа потребует явной гарантии жизненного цикла на
Vercel. Нельзя просто запускать фоновый поток в serverless и считать доставку
надёжной. Производственный RTT и накладные расходы live Supabase не измерялись.
