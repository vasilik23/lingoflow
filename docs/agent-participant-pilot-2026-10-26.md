## BP-26-ENV01 · этап восстановлен · P2 · verification-gap · QA / PO

**Наблюдение:** P01/P04/P05 в действующей сессии возвращались на вход;
P04 при повторе получил сообщение о слишком частых попытках. Logout ни один
участник не выполнял. Уверенность в наблюдении высокая, охват за пределами
общего QA неизвестен. Первоначально это блокировало три сценария.

**Диагностика:** узкая обезличенная выборка Supabase Auth logs за19:54–20:02:20
показала пять успешных `/logout`, три `/user`403 `session_not_found` и три
`/token`400 `refresh_token_not_found`. Два выхода19:58:23 и19:58:42 предшествовали
отказам. При одиночном повторе P05 журнал20:11–20:14:45 показал ещё один
`/logout`204 в20:12:38 и последующие403/400. До этого повторные входы были
остановлены до20:11, лимиты не обходились. В cookie-контексте P05 после
перенаправления auth-cookie отсутствовали; код auth middleware очищает их
после отказа проверки и обновления сессии.

Параллельно другой QA-процесс использовал тот же аккаунт. Его
[опубликованный отчёт](product-audit-2026-10-26.md) явно фиксирует logout
и время пересекающихся проверок. Это объясняет конфликт среды как рабочую
гипотезу, но каждый Auth-запрос конкретному процессу не атрибутирован.
Согласно [документации Supabase](https://supabase.com/docs/guides/auth/signout),
глобальный выход может отзывать другие сессии пользователя. Scope конкретных
выходов из этих агрегатов не установлен. Не утверждаем, что это новый
продуктовый дефект или что одновременные login сами по себе завершают сессии.

**Восстановление:** после окончания параллельной проверки повторять по очереди
без logout. У P05 это восстановило сохранённый шаг и позволило закончить урок.
Начальные ошибки не удаляются из протокола успешным повтором. Узкий поиск
Vercel logs по `Supabase Auth network request failed` не нашёл записей;
это не проверка всех ошибок production.

**Критерий:** восстановленные участники реально проходят заблокированные шаги.
Для будущего прогона выделить стабильное окно QA либо отдельно разрешённые
аккаунты. Если прерывание повторится без сторонних выходов — исследовать
изолированно. Усилие небольшое для координации; зависимость — доступность QA.
Это препятствие среды прогона, а не автоматически P1-баг приложения.
Секреты, IP, email, actor-ID, токены и сырые журналы в отчёт не включены.

Дополнительно проверен исходный код текущей версии: `sign_out()` в
[auth.py](../backend/polskiflow/auth.py) вызывает `/auth/v1/logout` без query scope.
В [официальной реализации Supabase Auth](https://github.com/supabase/auth/blob/master/internal/api/logout.go)
пустой scope выбирает `global`. Поэтому logout нашего приложения **может**
отзывать остальные сессии того же QA-аккаунта. Это подтверждение механизма,
а не атрибуция каждого наблюдавшегося выхода конкретному процессу и не
новый тест многосессионного поведения production.

Для этого этапа организационное восстановление принято: все прерванные шаги
пройдены. Код logout не менялся, исправление Auth не заявляется. Оставшийся
агентный шаг — только P04/P05 27 октября или позже в согласованном окне.
Человеческая beta, независимые аккаунты и проверка БД остаются за пределами
этой сверки. Повторные входы/logout при чтении отчёта не выполнялись.

Отдельная read-only SQL-сверка после чтения листов подтвердила для разрешённого
QA-аккаунта за 26 октября по одной строке `lesson_completions`:
`countries-quiz` — `cards_known/cards_total = 8/8`, `returns-grammar` — 5/5.
Это независимое подтверждение двух итоговых projections P04/P05. Оно не
проверяет все попытки, события или дубли аккаунта и не доказывает отдельное
владение результатами пяти ролей общего пользователя. Историческое ограничение
