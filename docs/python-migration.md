# Миграция LingoFlow на Python

Этот документ фиксирует поведение текущего MVP и служит контрактом для
поэтапного переноса приложения. Новая версия не считается совместимой, пока
перечисленные ниже пользовательские сценарии не воспроизведены и не покрыты
тестами.

## Подтверждённая инфраструктура

| Сервис | Ресурс | Роль |
| --- | --- | --- |
| GitHub | `vasilik23/polish-learn`, ветка `main` | исходный код и запуск деплоя |
| Vercel | проект `lingoflow-learn` | Django production и preview-деплои |
| Supabase | проект `vasilik23's Project`, `eu-west-1` | Auth и PostgreSQL |

Секреты не хранятся в репозитории. Локально Django использует
`SUPABASE_URL` и `SUPABASE_ANON_KEY` из окружения.

## Текущее поведение MVP

### Авторизация

1. Гость при открытии закрытой страницы перенаправляется на `/login`.
2. Пользователь может зарегистрироваться по email и паролю от 10 символов;
   обязательны строчная и заглавная буквы и цифра, распространённые комбинации
   блокируются до запроса в Supabase.
3. Пользователь может войти, выйти и вернуться на первоначально запрошенную
   страницу.
4. При первом использовании создаётся профиль с уровнем `A1` и именем из
   части email до `@`.

### Главная страница

1. Показывает имя, уровень, серию дней и дату.
2. Показывает четыре задания: слова, грамматика, повторение и тест.
3. Завершённые сегодня задания отмечаются в плане.
4. Прогресс плана вычисляется как доля завершённых заданий.

### Уроки

- **Слова:** пять карточек; пользователь открывает перевод и отвечает
  «Ещё раз» или «Знаю».
- **Грамматика:** теория и три вопроса с объяснениями.
- **Повторение курса:** использует карточки текущей темы; дневной план отдельно
  предлагает owner-scoped повторение личного словаря, когда по SM-2 есть слова
  со сроком на сегодня или раньше.
- **Тест:** пять вопросов с одним правильным вариантом и объяснением.
- Завершение урока сохраняет число заданий и правильных ответов за текущую
  UTC-дату.
- Первое завершение дня начинает или продолжает серию; пропуск дня сбрасывает
  её до одного.

### SM-2

- Поддерживаются две оценки: `again` (качество 1) и `know` (качество 5).
- `again` сбрасывает число успешных повторений и назначает повтор через день.
- Первые успешные интервалы — 1 и 6 дней; следующие умножаются на ease factor.
- Минимальный ease factor — 1.3.
- Тренировка личного словаря сначала выбирает карточки со сроком на сегодня или
  раньше, сохраняет новый интервал и позволяет отдельно фильтровать предстоящие
  повторения.

## Текущее состояние данных

Production развивается последовательными миграциями из `supabase/migrations/`:
пользовательские таблицы защищены RLS, учебный контент редактируется через
Django Admin, а служебные таблицы Django закрыты от `anon` и `authenticated`.
Номер отдельной ранней миграции больше не используется как описание актуального
состояния; источником порядка служат имена файлов в каталоге миграций.

Оставшиеся задачи развития данных:

1. Перейти с общей UTC-даты на часовой пояс пользователя.
2. Расширять форматы личного словаря, не ломая действующую owner-scoped
   SM-2-очередь и две оценки `again`/`know`.
3. Сохранить единый контракт прогресса для web, PWA и будущих mobile-клиентов.

### Подготовленный контракт Supabase → Django

- Модели Django являются неуправляемым (`managed = False`) отображением
  существующих таблиц. Команда `migrate` не выполняет DDL над данными Supabase.
- `003_sm2.sql` создаёт `flashcard_reviews` и может быть повторно проверен после
  неудачного запуска благодаря идемпотентному созданию политик.
- `004_harden_rls.sql` добавляет `WITH CHECK` в update-политики, закрывает
  прямой вызов trigger-функции регистрации и добавляет delete-политику карточек.
- SQL применён к production и проверен Supabase Security Advisor. Новые изменения
  по-прежнему проходят preview, проверку RLS и отдельное подтверждение production.
- Переходный Django API принимает Supabase access token как Bearer token и
  проверяет его через Supabase Auth; JWT secret и service-role key приложению не
  передаются.

## Целевая архитектура

- Python 3.11 или новее (локальные проверки выполняются на 3.11; production
  можно обновлять независимо).
- Django как веб-фреймворк и административная панель.
- Django Templates + HTMX для интерактивного интерфейса без отдельного
  React-приложения.
- PostgreSQL; на первом этапе остаётся подключённый Supabase.
- pytest для доменных, API- и интеграционных тестов.
- Контент уроков хранится в базе и редактируется через Django Admin.

### Критерии отключения legacy-приложения

- Основной домен ведёт на Django, а login → урок → чтение → словарь → тренировка
  проходит в production без ошибок.
- Переменные окружения и Supabase Auth redirect URLs настроены для Django-домена.
- Старый Vercel-проект отключён только после успешной production-проверки и
  зафиксированного способа отката.
- После удаления Next.js повторно проходят Python CI, Django deployment и аудит
  отсутствующих/неиспользуемых файлов.

### Правила наполнения контентом

Подробные правила находятся в [`content-sources.md`](content-sources.md), а
последовательность A1–C2 — в [`content-roadmap.md`](content-roadmap.md).

- До импорта материал проверяется по первоисточнику в интернете.
- Разрешены собственные материалы, public domain и совместимые открытые лицензии.
- Для каждой внешней основы сохраняются URL, автор, лицензия, дата проверки и
  описание внесённой адаптации.
- Структура наполнения идёт по CEFR: темы → тексты → glossary → упражнения;
  сначала формируется связный A1, затем последовательно A2, B1, B2 и C1.

## Правило разработки и доставки

Для каждого следующего этапа используется один и тот же цикл:

1. отдельная ветка и небольшое изменение;
2. локальные lint и тесты;
3. pull request в GitHub;
4. preview-деплой Vercel;
5. проверка приложения и схемы Supabase;
6. merge в `main` и production-деплой;
7. проверка production-логов и ключевого пользовательского сценария.
