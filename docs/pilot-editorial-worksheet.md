# Рабочий лист редактора трёх пилотов

Это инструкция и незаполненный протокол независимой проверки BM-01/02.
Подготовка пакета и этот документ не означают приёмку. Приоритет и порядок
работ остаются в [едином плане](../README.md#единый-план-работ).

## До начала

Оператор формирует [приватный пакет](pilot-editorial-review.md#сборка),
проверяет SHA-256 файлов по `manifest.json` и передаёт его редактору по
согласованному каналу. Редактор получает все три HTML, `snapshot.json` и
бланк заметок; доступ к аккаунтам учеников не нужен. Ключи ответов не
публикуются. Для замечаний использовать вымышленные примеры, без реальных
писем, имён, email и записей учеников.

В отдельной рабочей копии заметок зафиксировать:

| Поле | Значение для заполнения |
| --- | --- |
| Редактор и квалификация | Имя/согласованный идентификатор; опыт польского и методики; участие в создании исходного материала |
| Проверенные языки | RU / PL / EN; неподтверждённые языки обозначить явно |
| Дата, версия | Дата проверки, declared source commit, `snapshot_sha256` |
| Источник содержимого | Какая изолированная content-БД; отдельное доказательство соответствия целевой БД либо «не проверено» |
| Объём | Все три темы / точный ограниченный объём; пропущенные элементы и причина |

Не менять контрольные суммы и исходный `manifest.json` после заполнения
заметок: он описывает выданный пакет, а не последующую работу редактора.
Изменённая рабочая копия `review-notes.json` уже не соответствует его хешу.
Сохранить исходный пакет отдельно; вернуть заметки с исходным checksum.

## Маршруты и наблюдаемый результат

Чтение идёт после третьего урока и перед comprehension-проверкой. Сверять
HTML со `snapshot.json`, а не предполагать порядок из алфавитной сортировки.

| Тема / стабильный ID | Уроки в порядке маршрута | Чтение | Проверяемое самостоятельное действие |
| --- | --- | --- | --- |
| A1 · `introductions` | `words` → `grammar` → `review` → чтение → `a1read-kurs-check` → `quiz` | `pierwszy-dzien-na-kursie` | 3–4 предложения: представиться, сказать откуда, задать два вопроса |
| A2 · `housing-services` | `housing-words` → `housing-grammar` → `housing-review` → чтение → `housing-reading-check` → `housing-quiz` | `usterka-w-mieszkaniu` | Сообщить владельцу о конкретной неисправности, вежливо попросить помощь, предложить время ремонта |
| B1 · `b1-biography` | `bio-words` → `bio-grammar` → `bio-review` → чтение → `bio-reading-check` → `bio-quiz` | `bio-droga-joanny` | Связный ответ 5–7 предложений: фон, решение, причина и результат |

Для каждой темы сначала прочитать цель и самостоятельно составить ответ,
не копируя sample. Затем пройти карточки, теорию, все вопросы, чтение и
глоссарий; отметить, каких средств не хватило для ответа. Sample служит
одним примером: другие грамматически корректные ответы должны приниматься
редактором. Достижимость цели нельзя доказать одним количеством карточек.

## Рубрика для восьми критериев

В рабочем `review-notes.json` сохранять существующие ключи `criteria`.
Значения: `"pass"` — проверен весь заявленный объём; `"change"` — есть
конкретный дефект; `"blocked"` — для решения не хватает данных/компетенции;
`null` — ещё не проверено. Это договорённость для ручной работы: приложение
не валидирует и не импортирует эти значения, они не запускают promotion.

| Ключ | Что проверить, прежде чем поставить pass |
| --- | --- |
| `goal_alignment` | Каждый этап готовит заявленное действие; лексика и конструкции достаточны для собственного ответа; нет неожиданного требования вне показанного материала. Уровень оценён методистом, не выведен из количества слов. |
| `natural_polish` | Все польские задания, варианты, примеры и текст естественны, согласованы грамматически; регистр соответствует адресату, нет случайного смешения обращения и форм рода. |
| `translations` | Поддержка каждого заявленного RU/PL/EN языка сохраняет смысл и ограничения задания, не раскрывает ответ, не содержит остаточных чужих меток. Проверить также пример, чеклист и глоссарий. |
| `unique_answers` | У каждого закрытого вопроса ровно один правильный вариант при данном контексте; distractors правдоподобны, но не допустимы как альтернативный ответ. Проверить все варианты, а не только ключ. |
| `explanations` | Разбор объясняет правило или конкретное место в тексте, соответствует ключу, помогает исправить ошибку и не противоречит показанной теории. |
| `reading_and_glossary` | Текст понятен целевому уровню; для A-уровня оценить долю знакомой/выводимой лексики и опору на контекст. Глоссарий соответствует форме в тексте; comprehension проверяет сам текст без внешних знаний. |
| `own_response` | Инструкция, sample и чеклист согласованы; самостоятельно составленный ответ выполняет цель изученными средствами; самооценка не выдаётся за объективный экзаменационный балл. |
| `sources` | Для использованного материала доступны происхождение и атрибуция; условия использования понятны. Внешние источники без подтверждения прав отмечены blocked. Original-метаданные сами по себе не доказывают качество. |

Если найден дефект, указать его и в `findings`; `change` без ссылки на
элемент не даёт разработчику воспроизводимого задания. Если язык не проверен,
`translations` нельзя считать безусловным pass для всех трёх языков:
ограничение зафиксировать в finding и итоговом решении.

## Формат одного замечания

Пример структуры ниже не является найденным багом. Имена дополнительных
полей — ручная договорённость, не API импорта.

```json
{
  "id": "EDITOR-001",
  "criterion": "unique_answers",
  "language": "pl",
  "ref": "<lesson_id>:q:<position из snapshot.json>",
  "severity": "blocking",
  "fragment": "<точный короткий фрагмент>",
  "reason": "<почему ответ неоднозначен в этом контексте>",
  "proposed_fix": "<предложенная формулировка и основание>",
  "status": "open"
}
```

Finding помещается в `findings` соответствующей темы. Для вопроса брать
`ref` из snapshot, не ID строки БД; для карточки указать lesson + card ID,
для чтения — reading ID + номер абзаца/слово глоссария, для цели — topic ID
+ имя поля (`goal`, `prompt`, `checks`, `sample`).

`blocking` — неверный/неоднозначный ключ, ошибка в польском правиле,
недостижимая цель или неподтверждённые права на материал.
`minor` — редакционная неточность без изменения смысла и проверки знаний.
Если влияние неизвестно, оставить вопрос открытым, не снижать важность
автоматически. Техническая поломка маршрута передаётся отдельно в QA.

## Решение и повторная проверка

1. Вернуть заметки по всем трём темам: восемь критериев заполнены либо
   явно оставлены непроверенными с причиной; у каждого дефекта точный ref.
2. Оператор сводит findings в исправления. Даже принятый minor не исчезает
   молча: фиксируется решение и ответственный. Открытый blocking исключает
   рекомендацию выпуска соответствующей темы.
3. После изменения контента, перевода или renderer собрать новый пакет.
   Передать редактору новый checksum, список изменённых refs и связанных
   объяснений, ключей и переводов. Старый pass не переносить автоматически.
4. Редактор подтверждает исправленные элементы и отсутствие противоречий
   в связанных шагах. В решении указать темы, языки, checksum, дату,
   оставшиеся ограничения и `recommended` / `changes_required` / `blocked`.
5. Решение редактора не устанавливает `release_authorized=true` и не
   закрывает пользовательскую PA-04, техническую проверку или promotion
   receipt. Выпуск проходит существующий отдельный workflow.
