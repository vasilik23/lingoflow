# Проверка сроков хранения без удаления

`ops/retention-review.mjs` — локальный инструмент анализа подготовленного
оператором snapshot. Он не подключается к БД или почте, не выполняет DELETE,
не отправляет предупреждения и не запускается по расписанию. Статус
`deletion_review` означает необходимость ручной и повторной live-проверки,
а не разрешение удалить строку по старому отчёту.

## Правила

- Аккаунт: 12 календарных месяцев от последнего подтверждённого использования,
  затем подтверждённая доставка предупреждения и 30 суток ожидания.
  29 февраля при добавлении 12 месяцев переходит на 28 февраля.
- Полнота учёта активности обязательна: `activity_complete: true` можно
  указывать лишь при полном учёте использования, а не только уроков или входов.
  `profiles.last_active_date` само по себе этого не доказывает.
- Доставка должна произойти после порога неактивности. Подтверждённый момент
  активности на дату доставки должен совпасть с последней активностью
  snapshot. Любая новая активность отменяет прежнее основание удаления.
- Обращения: 180 суток после подтверждённого закрытия. Старый `created_at`
  не заменяет `closed_at`. Открытые обращения сохраняются; неизвестный статус,
  отсутствующие/невозможные даты отправляются на ручную проверку.
- Время сравнивается как UTC instants; 30 и 180 суток — интервалы по 24 часа.
  Snapshot не может быть из будущего или старше 24 часов.
- Повторная проверка текущей активности/статуса и подтверждённых удалений
  после restore обязательна перед любым будущим реальным удалением.

## Формат и запуск

Подготовить JSON на зашифрованном рабочем томе вне репозитория, файл `0600`,
каталог `0700`. Пример синтетических данных:

```json
{
  "version": 1,
  "captured_at": "2026-10-23T09:00:00Z",
  "accounts": [{
    "user_id": "11111111-1111-4111-8111-111111111111",
    "created_at": "2024-01-01T00:00:00Z",
    "last_activity_at": "2025-09-01T00:00:00Z",
    "activity_complete": false,
    "warning": null
  }],
  "feedback": [{
    "id": "22222222-2222-4222-8222-222222222222",
    "status": "resolved",
    "created_at": "2026-09-01T00:00:00Z",
    "closed_at": null
  }]
}
```

Для подтверждённого предупреждения поле `warning` содержит `delivered_at`
и `activity_at_delivery` (ISO timestamp с timezone). Передавать только реально
подтверждённую доставку, не факт создания письма или запуска workflow.

```sh
node ops/retention-review.mjs /private/path/input.json /private/path/report.json
node --test ops/retention-review.test.mjs
```

Дата snapshot в примере иллюстративная; для реального запуска нужен свежий
snapshot. В stdout только агрегаты; UUID остаются в приватном отчёте. Email,
текст обращения, пароль и произвольные дополнительные поля не копируются.
Выходной файл создаётся эксклюзивно с `0600`, перезапись запрещена. Входные
symlink/hardlink и общедоступные файлы отклоняются. Отчёты содержат персональные
идентификаторы: не добавлять их в Git/CI artifacts или публичные документы.

## Историческая исходная схема · до среза 23 октября 2026

Read-only запрос `information_schema.columns` подтвердил:

- `profiles` имеет `created_at`, `last_active_date`, но не полный журнал
  использования приложения;
- `user_feedback` имеет `created_at` и `status`, но не `closed_at`/`resolved_at`.

Это исходное состояние заменено [срезом реальных данных](live-retention-evidence-2026-10-23.md):
добавлены DB timestamps активности и закрытия, RLS сохранена. Новые даты
не дают исторической или непрерывной полноты наблюдений. Автоматические jobs,
удаления и письма по-прежнему не включены.

## Получить отчёт из реальной базы

Оператор с авторизованным Supabase CLI 2.120.0 может выполнить SELECT
через Management API; пароль БД не нужен. Создать каталог на зашифрованном
томе вне репозитория с правами 0700, затем:

```sh
set -o pipefail
supabase db query --project-ref habcghygjaynknkcbirz --linked --output json --file ops/retention-snapshot.sql | node ops/retention-live-report.mjs /private/encrypted/retention-report
```

Форма SQL-результата: один элемент массива с колонкой `retention_snapshot`.
При другой форме инструмент останавливается до записи. Ни stdout запроса,
ни UUID не передавать в argv, чат или CI artifacts. На этой машине CLI без
login, поэтому приёмочный snapshot прочитан авторизованным MCP, а проверенный
доменный алгоритм выполнен в текущей среде. На диск перенесены только агрегаты.
Адаптер с приватными файлами проверен на синтетических данных.

Свежие известные даты доказывают active даже при неполной истории. Для
утверждения неактивности по-прежнему требуется `activity_complete=true`;
реальный snapshot этого флага автоматически не устанавливает. Окно запросов
учитывается консервативной верхней границей +15 минут (не позже snapshot).
До реального удаления потребуются повторная проверка актуальных данных и
подтверждённая доставка предупреждения.
